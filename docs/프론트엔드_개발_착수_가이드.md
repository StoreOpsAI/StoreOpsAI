# StoreOps AI 프론트엔드 개발 착수 가이드

## 1. 문서 목적

이 문서는 StoreOps AI 요구사항 명세서를 바탕으로 React와 Vite를 사용해 점주 화면을 개발할 때의 시작 순서와 구현 기준을 정리한 문서입니다.

프런트엔드는 사건 확인, 발주 승인, 질문 조회라는 세 가지 업무를 점주가 빠르게 판단할 수 있도록 보여 주는 역할을 담당합니다. AI 모델의 내부 처리보다 서버 API 응답, 상태 표시, 점주 조작 결과를 정확하게 표현하는 것을 우선합니다.

## 2. 현재 프로젝트 상태

현재 프런트엔드는 다음 구성으로 되어 있습니다.

- React 19
- Vite
- `src/App.jsx`의 점주 인증 및 사건 업무 화면
- `src/api/auth.js`, `src/api/client.js`, `src/api/events.js`의 API 호출 모듈
- 회원가입, 로그인, 세션 복원, 로그아웃 화면
- 사건 목록·상세 조회와 상태 변경 화면
- Vite 개발 서버 `5173` 포트
- `/api` 요청을 FastAPI `http://localhost:8000`으로 전달하는 프록시

인증되지 않은 사용자는 `/api/auth/me` 확인 후 로그인·회원가입 화면으로 이동하며, 인증된 사용자만 사건 API를 호출합니다.

## 3. 첫 번째 개발 목표

첫 번째 목표인 **회원가입·세션 인증과 사건 목록 조회부터 사건 상태 변경까지의 화면 흐름**을 완료했습니다.

```text
회원가입 또는 로그인
    -> 세션 ID 발급
    -> /api/auth/me 세션 복원
    -> FastAPI 사건 API
    -> 사건 목록 조회
    -> 사건 선택
    -> 사건 상세 표시
    -> 확인·오탐·처리 완료 선택
    -> 서버 상태 변경
    -> 화면 데이터 갱신
```

발주와 질문 화면은 사건 화면의 API 연결과 상태 처리 패턴을 만든 뒤 확장합니다.

## 4. 화면 개발 순서

### 4.1 1단계: 공통 화면 틀

현재 다음 공통 요소가 구현되어 있습니다.

- 로그인 및 회원가입 입력 화면
- 세션 확인 중 로딩 상태
- 로그아웃 버튼
- 상단 서비스 이름과 현재 매장 표시
- 사건, 발주, 질문 탭
- 현재 API 연결 상태
- 로딩 상태
- 오류 상태
- 빈 데이터 상태

처음에는 별도의 라우터 없이 탭 상태로 구현해도 됩니다. 화면 수가 늘어나거나 URL별 접근이 필요해지면 React Router를 추가합니다.

### 4.2 2단계: 사건 화면

사건 목록에는 다음 정보를 표시합니다.

- 사건 번호
- 사건 종류
- 발생 시각
- 카메라 번호
- 현재 상태
- 발생 경로

사건 상세에는 다음 정보를 표시합니다.

- 10초 사건 영상 또는 영상 없음 안내
- 카메라 번호
- 발생 시각
- 다섯 행동 분류 점수
- 기준값
- VLM 설명 상태
- VLM의 관찰 내용
- VLM의 불확실한 점
- 점주가 확인할 일
- 상태 변경 버튼

점수는 사고 확률이 아니라 다섯 분류 사이의 상대적인 점수라는 안내를 표시해야 합니다. VLM 설명은 행동 분류 판단의 근거가 아니라 참고 정보라는 안내도 표시합니다.

상태 버튼은 현재 상태에 따라 활성화 여부를 결정합니다.

```text
미확인 -> 확인
미확인 -> 오탐
확인   -> 처리 완료
```

허용되지 않은 상태 변경은 서버에서 거부되지만, 프런트에서도 불필요한 버튼을 비활성화해 점주의 실수를 줄입니다.

### 4.3 3단계: 발주 화면

발주 추천 목록에는 다음 정보를 표시합니다.

- 상품 번호
- 대상 날짜
- 내일 수요
- 모레 수요
- 총 예상 수요
- 추천 수량
- 추천 박스 수
- 도착 전 부족 수량
- 자료 구분: 실제 자료 또는 합성 자료
- 승인 상태

발주 상세 또는 승인 영역에서는 다음을 처리합니다.

- 추천 수량을 수정
- 개수와 박스 수 표시
- 승인자와 승인 시각 표시
- 승인해도 공급사에 주문이 전송되지 않는다는 안내 표시
- 추천 수량이 품절을 보장하지 않는다는 안내 표시

승인 요청 중에는 중복 제출을 막고, 성공 후 서버가 반환한 값을 기준으로 화면을 갱신합니다. 프런트에서 재고나 공급사 전송 여부를 임의로 변경하지 않습니다.

### 4.4 4단계: 질문 화면

질문 화면에는 다음 영역이 필요합니다.

- 질문 입력창
- 질문 제출 버튼
- 답변 영역
- 출처 영역
- 조회 조건 영역
- 답변 처리 중 상태
- 조회 실패와 0건 결과 안내

답변에는 다음 정보를 구분해서 표시합니다.

- 답변 내용
- 기록 조회 출처 또는 매뉴얼 문서명·버전·절
- 실제 사용한 매장 번호와 날짜 범위
- 도구 호출 결과
- 자료가 없거나 근거가 부족한 경우의 안내

## 5. API 연결 기준

프런트엔드는 Vite 프록시를 통해 상대 경로로 API를 호출합니다.

```javascript
fetch("/api/events");
```

개발 환경에서 프런트엔드와 백엔드를 따로 실행해도 `/api` 요청은 FastAPI 서버로 전달됩니다.

우선 연결할 API는 다음과 같습니다.

| 화면 | 메서드 | 경로                                    | 용도                           |
| ---- | ------ | --------------------------------------- | ------------------------------ |
| 인증 | POST   | `/api/auth/signup`                      | 매장과 점주 계정 생성          |
| 인증 | POST   | `/api/auth/login`                       | 세션 ID 발급                   |
| 인증 | POST   | `/api/auth/logout`                      | 세션 폐기                      |
| 인증 | GET    | `/api/auth/me`                          | 현재 로그인 사용자와 매장 확인 |
| 사건 | GET    | `/api/events`                           | 사건 목록 조회                 |
| 사건 | GET    | `/api/events/{event_id}`                | 사건 상세 조회                 |
| 사건 | POST   | `/api/events/{event_id}/status`         | 사건 상태 변경                 |
| 발주 | GET    | `/api/orders/drafts`                    | 발주 추천 조회                 |
| 발주 | POST   | `/api/orders/drafts/{draft_id}/approve` | 발주 승인                      |
| 질문 | POST   | `/api/ask`                              | 질문 전송과 답변 조회          |
| 질문 | GET    | `/api/ask/{session_id}/log`             | 질문 실행 로그 조회            |

공통 API 처리 함수는 컴포넌트마다 반복하지 말고 별도 파일로 분리합니다.

```text
frontend/src/
├─ api/
│  ├─ client.js
│  ├─ auth.js
│  ├─ events.js
│  ├─ orders.js
│  └─ questions.js
```

API 오류는 HTTP 상태 코드와 응답 메시지를 함께 확인합니다. 서버 오류를 빈 목록으로 바꾸어 표시하면 안 됩니다.
인증 API는 로그인 응답의 세션 ID를 사용합니다. 세션 ID는 프런트엔드 메모리 상태에 보관하고, 보호 API 요청마다 `X-Session-ID` 헤더로 전달합니다. 회원가입 성공 후에는 로그인 API를 호출해 세션 ID를 발급합니다.

## 7. 화면 상태 처리

각 화면은 최소한 다음 상태를 구분해야 합니다.

```text
idle       최초 상태
auth       세션 확인 또는 인증 화면
loading    API 요청 중
success    정상 응답
empty      정상 응답이지만 데이터 없음
error      서버 또는 네트워크 오류
submitting 등록·승인·상태 변경 중
```

특히 다음을 서로 다르게 표시합니다.

- 데이터가 0건인 경우
- 서버 조회에 실패한 경우
- 자료가 아직 수집되지 않은 경우
- VLM 설명이 아직 처리 중인 경우
- 영상이 없는 카메라 끊김 사건인 경우

## 8. 첫 번째 작업 목록

다음 작업을 첫 번째 프런트엔드 개발 묶음으로 완료했습니다.

1. 회원가입·로그인·세션 복원 화면 작성
2. 인증 API와 X-Session-ID 헤더 연결
3. 로그아웃과 보호 API 접근 처리
4. 사건 업무 화면 레이아웃 작성
5. 사건 목록·상세 조회와 상태 변경 연결
6. 로딩·오류·빈 목록 상태 추가
7. 사건 점수와 VLM 상태 표시
8. 모의 사건 `E014`, `E015`로 화면 확인

첫 번째 묶음이 끝나면 다음 요구사항을 우선 확인할 수 있습니다.

- `FR-UI-01` ~ `FR-UI-05`
- `FR-REC-02`
- `FR-EVT-08`
- `FR-EVT-15`의 VLM 대기 상태 표시

## 9. 프런트엔드 구현 원칙

- API 응답을 받기 전에는 로딩 상태를 표시합니다.
- API 오류를 0건 결과처럼 표시하지 않습니다.
- 서버가 반환한 상태와 이력을 기준으로 화면을 갱신합니다.
- 상태 변경과 승인 버튼은 요청 중 중복 클릭을 막습니다.
- 영상이 없는 끊김 사건에는 영상 플레이어 대신 이유를 표시합니다.
- VLM 상태가 `pending`이면 `준비 중`, `failed`이면 실패 안내를 표시합니다.
- 합성 자료와 실제 자료를 배지나 문구로 구분합니다.
- 한국 시간의 ISO 8601 값을 점주가 읽기 쉬운 형식으로 변환해 표시합니다.
- 긴 답변, 출처, 오류 문장이 화면 밖으로 잘리지 않도록 합니다.
- 사건 점수는 사고 확률로 표현하지 않습니다.
- 세션 ID는 브라우저 영구 저장소에 저장하지 않고 프런트엔드 메모리에서 관리합니다.
- 로그인하지 않은 사용자는 사건 목록과 상태 변경 API를 호출할 수 없습니다.
- 공급사 주문이 실제로 전송되지 않는다는 안내를 발주 화면에 표시합니다.

## 10. 개발 및 검증 명령

### 백엔드 실행

프런트엔드 API 연결을 확인하려면 먼저 FastAPI 서버를 실행합니다.

```powershell
cd backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

헬스 체크 주소는 다음과 같습니다.

```text
http://localhost:8000/api/health
```

### 프런트엔드 실행

```powershell
cd frontend
npm install
npm run lint
npm run build
npm run dev -- --host 0.0.0.0
```

개발 화면 주소는 다음과 같습니다.

```text
http://localhost:5173
```

### 첫 화면 완료 기준

- 사건 목록에서 `E014`, `E015`가 표시됩니다.
- 회원가입 후 자동 로그인되고 새로고침 뒤에도 세션이 복원됩니다.
- 로그아웃 후 사건 API 접근이 차단됩니다.
- 사건 번호, 종류, 시각, 카메라, 상태가 표시됩니다.
- 사건 상세에서 영상 또는 영상 없음 안내가 표시됩니다.
- 행동 분류 점수와 기준값이 표시됩니다.
- VLM `pending` 상태가 `준비 중`으로 표시됩니다.
- 허용된 상태 변경 버튼만 활성화됩니다.
- 상태 변경 성공 후 최신 사건 정보가 화면에 반영됩니다.
- 빈 목록, 네트워크 오류, 서버 오류를 구분해 표시합니다.
- `npm run lint`와 `npm run build`가 통과합니다.

## 11. 다음 개발 순서

사건 화면이 완료된 후 다음 순서로 진행합니다.

1. 발주 추천 목록과 수량 수정·승인 화면
2. 승인 이력과 합성 자료 표시
3. 질문 입력·답변·출처 화면
4. 질문 조회 조건과 도구 실행 로그 화면
5. SSE를 이용한 새 사건 알림
6. 실제 영상, VLM, Agent API 연결

프런트엔드는 서버가 제공하는 API 계약을 기준으로 개발하고, 실제 AI 모델의 내부 구현에는 의존하지 않아야 합니다. 따라서 모의 응답으로도 모든 화면의 로딩, 성공, 빈 결과, 오류 상태를 먼저 확인할 수 있어야 합니다.
