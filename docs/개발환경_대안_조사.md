## 1. 조사 목적과 범위

현재 Windows 로컬에서 실행 중인 StoreOps AI를 다른 개발 환경으로 옮길 수 있는 방법을 조사한 문서이다. 이 문서는 조사 결과와 도입 방향만 기록하며, Dockerfile, Compose 파일, Dev Container 설정, WSL 설치 또는 원격 환경 생성은 수행하지 않았다.

- 조사일: 2026-09-18
- 대상: Docker 기반 환경과 로컬 외 개발 환경
- 기준: 현재 저장소의 실행 구조와 공식 문서

### 3.1 Docker Compose

Docker 공식 문서는 Docker를 애플리케이션 실행에 필요한 것을 포함한 격리된 컨테이너로 패키징하는 기술로 설명한다. 또한 Docker Compose는 여러 컨테이너 애플리케이션의 서비스, 네트워크, 볼륨을 YAML 하나로 정의하고 한 번에 시작·중지·로그 확인할 수 있는 도구로 설명한다.

이 프로젝트에 적용할 경우의 개념적 구성은 다음과 같다.

```text
frontend (Vite, 5173) -> backend (FastAPI, 8000)
                                  -> db (향후 PostgreSQL 16, 선택)
```

현재 Vite 프록시의 `localhost:8000`은 프런트엔드 컨테이너 안에서 해석될 수 있으므로, 두 서비스를 별도 컨테이너로 실행할 때는 Compose 서비스명 기반 주소로 바꾸는 검토가 필요하다. 이 변경은 아직 수행하지 않았다.

**판단:** 프런트엔드와 백엔드뿐 아니라 향후 PostgreSQL과 `pgvector`를 함께 다룰 가능성이 있으므로, 팀 단위 재현성과 서비스 간 네트워크를 중시한다면 1순위다.

### 3.2 Docker Compose + VS Code Dev Containers

VS Code 공식 문서에 따르면 Dev Containers 확장은 컨테이너를 완전한 개발환경으로 사용하게 하며, 프로젝트의 `devcontainer.json`으로 도구와 런타임 구성을 정할 수 있다. 공식 Dev Container 가이드는 Compose 파일에서 개발용 서비스와 PostgreSQL 같은 지원 서비스를 함께 정의하는 방식도 제시한다.

이 방식은 다음 두 가지를 결합한다.

- Compose: 애플리케이션 서비스와 DB의 실행·네트워크 관리
- Dev Container: VS Code 터미널, 디버거, 확장, 개발 도구가 실행될 위치 관리

Windows에서는 Docker Desktop과 WSL 2 백엔드 사용이 일반적인 전제이며, VS Code 문서는 Windows와 macOS의 소스 바인드 마운트에 성능 오버헤드가 있을 수 있다고 안내한다. 소스 위치와 볼륨 전략을 함께 결정해야 한다.

**판단:** 현재 사용자가 VS Code에서 개발하고 있고, “내 PC에 설치된 Python/Node 상태”를 줄이고 싶은 목적이라면 가장 균형이 좋다.

### 3.3 WSL 2

Microsoft 문서에 따르면 WSL은 별도 가상머신이나 듀얼부트 없이 Windows에서 Linux 배포판과 Linux 도구를 사용할 수 있게 한다. WSL 2는 경량 가상머신 안에서 Linux 커널을 사용하고 WSL 1보다 파일 시스템 성능과 시스템 호출 호환성을 높인다.

VS Code의 WSL 확장을 사용하면 명령, 디버깅, 터미널을 WSL 안에서 실행할 수 있다. 이 방식은 Docker 없이도 현재의 `npm`과 Python 실행 흐름을 Linux 환경으로 옮기는 선택지다.

**판단:** 컨테이너 이미지보다 Linux 개발환경이 필요한 경우 적합하다. 다만 WSL은 컨테이너 격리나 서비스별 실행 구성을 제공하는 도구가 아니므로, Compose의 대체재라기보다 실행 기반을 Linux로 바꾸는 방법이다.

### 3.4 Remote-SSH

VS Code 공식 문서에 따르면 Remote-SSH는 원격 머신, VM 또는 SSH 서버가 실행 중인 컨테이너의 폴더를 로컬 VS Code에서 열고, 명령과 확장을 원격 호스트에서 실행한다. 포트 포워딩으로 원격 개발 서버를 로컬에서 확인할 수도 있다.

필요 조건은 다음과 같다.

- 로컬의 OpenSSH 호환 클라이언트
- 원격 호스트의 SSH 서버
- 원격 호스트의 지원 운영체제와 최소 자원
- 인증 방식, 방화벽, 포트 포워딩 정책

**판단:** 사내 Linux 서버나 개발 VM이 이미 있다면 유용하다. 현재 저장소만으로는 연결할 원격 호스트 정보가 없으므로 실제 적용 가능 여부는 **없음(확인할 인프라 정보 없음)**이다.

### 3.5 GitHub Codespaces

GitHub 공식 문서에 따르면 Codespace는 GitHub가 가상머신 위 Docker 컨테이너로 제공하는 클라우드 개발환경이다. 저장소에 Dev Container 설정을 커밋하면 반복 가능한 환경으로 구성할 수 있고, 브라우저·VS Code·GitHub CLI로 접속할 수 있다.

장점은 개발 PC의 Windows, Node, Python 설치 상태와 무관하게 Linux 환경을 사용할 수 있다는 점이다. 반면 개인·조직 계정의 사용량 쿼터, 결제 수단, 저장소 권한과 네트워크 정책을 확인해야 한다.

**판단:** 팀원이 여러 OS를 사용하거나 사양이 낮은 PC에서 개발해야 할 때 고려할 수 있다. 이 저장소에 Codespaces 설정은 **없음**이며, 계정의 사용 한도와 비용은 이 저장소만으로 판단할 수 없다.

## 4. 이 프로젝트에 대한 권장 방향

### 1순위: Compose를 기반으로 한 Dev Container

권장 대상은 다음 구성이다.

1. `frontend` 서비스: Node 기반 Vite 개발 서버
2. `backend` 서비스: Python 기반 FastAPI/Uvicorn 개발 서버
3. `db` 서비스: PostgreSQL 16 이상을 도입할 때 추가
4. `.devcontainer/devcontainer.json`: VS Code 연결 대상과 포트, 확장, 초기화 명령 관리

도입 시 결정해야 할 사항은 다음과 같다.

- 개발용 이미지의 Node와 Python 버전 고정 방식
- `5173`, `8000`, 향후 DB 포트의 노출 및 포워딩 방식
- 소스 코드 바인드 마운트와 컨테이너 볼륨의 선택
- 컨테이너 내부 프록시 주소: `localhost` 대신 Compose 서비스명 사용 여부
- PostgreSQL 데이터의 영속 볼륨과 초기화 방식
- 비밀값을 저장하지 않는 환경변수 전달 방식
- Windows 파일 시스템에서의 파일 감시와 의존성 디렉터리 처리

### 대안 선택 기준

- Docker 설치가 가능하고 서비스 재현성이 중요함: **Compose + Dev Containers**
- Docker 없이 Linux 도구만 필요함: **WSL 2**
- 실행 자원을 별도 서버로 분리해야 함: **Remote-SSH**
- 개발 PC를 사실상 사용하지 않고 클라우드에서 작업함: **Codespaces**

## 6. 도입 후 검증 기준

설정 구현을 시작할 때는 다음 순서로 확인하는 것이 적절하다.

1. 컨테이너 빌드와 의존성 설치가 재현되는지 확인
2. 백엔드 `GET /api/health`가 정상 응답하는지 확인
3. 프런트엔드에서 `/api` 프록시가 백엔드에 연결되는지 확인
4. 프런트엔드 `npm run lint`, `npm run build` 실행
5. 백엔드 `python -m compileall app` 및 기존 테스트 실행
6. 컨테이너 재생성 후에도 개발 데이터와 필요한 DB 데이터가 의도대로 유지되는지 확인
7. Windows, WSL 또는 원격 환경에서 포트와 파일 감시가 정상인지 확인

## 7. 결론

현재 상태에서 Docker 기반 개발환경을 만들 수 있는 근거는 충분하지만, 저장소에는 Docker 실행 설정이 아직 **없음**이다. 가장 적합한 설계 후보는 `Docker Compose + VS Code Dev Containers`이며, Docker를 사용하지 않는 대안으로 `WSL 2`, 별도 호스트를 사용하는 `Remote-SSH`, 클라우드 기반 `GitHub Codespaces`가 있다.

이번 조사에서는 문서만 추가했으며, 어떤 대안도 실제로 설치·생성·실행하지 않았다.
