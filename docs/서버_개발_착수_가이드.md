# StoreOps AI 서버 개발 착수 가이드

## 1. 문서 목적

이 문서는 StoreOps AI 요구사항 명세서를 바탕으로 React 화면과 Python FastAPI 서버를 개발할 때의 시작 순서와 담당 범위를 정리한 문서입니다.

처음부터 YOLO, I3D, VLM, LLM을 모두 연결하지 않고, 모의 데이터로 핵심 업무 흐름을 먼저 완성합니다. 이후 실제 모델과 데이터를 기존 API 계약에 연결합니다.

## 2. 현재 프로젝트 상태

현재 프로젝트에는 다음 기능이 구현되어 있습니다.

- FastAPI 서버의 `/api/health` 헬스 체크
- FastAPI 서버의 `/api/echo` 연결 확인 API
- React에서 백엔드 상태 확인
- Vite의 `/api` 요청을 `localhost:8000`으로 전달하는 프록시
- 모의 사건 `E014`, `E015`의 목록·상세 조회
- 사건 상태 변경과 상태 변경 이력 조회
- 회원가입, 로그인, 로그아웃, 로그인 사용자 조회
- 세션 ID 발급과 세션 만료·폐기 검증
- 로그인한 점주의 매장 번호로 범위가 제한된 사건 조회·상태 변경
- `DATABASE_URL` 설정 시 PostgreSQL 저장소로 전환, 미설정 시 메모리 저장소 사용

현재 구현은 `DATABASE_URL` 환경변수 유무로 저장소를 전환합니다. 값이 없으면 메모리 저장소를, 값이 있으면 PostgreSQL 저장소(`PostgresAuthRepository`, `PostgresEventRepository`)를 사용합니다. 메모리 저장소는 서버를 재시작하면 데이터가 초기화됩니다.

아직 구현되지 않은 주요 항목은 다음과 같습니다.

- 발주 승인 API
- 질문 Agent와 조회 도구
- 실제 업무 화면(발주, 질문)

## 3. 첫 번째 개발 목표

첫 번째 목표는 **사건 후보 등록부터 점주 상태 변경까지의 한 흐름을 완성하는 것**입니다.

```text
모의 사건 데이터
    -> FastAPI 저장
    -> React 사건 목록
    -> 사건 상세 조회
    -> 점주 상태 변경
    -> 상태 변경 이력 저장
```

이 흐름을 먼저 완성하면 실제 영상 파이프라인이 준비되지 않아도 서버, 화면, DB의 연결을 검증할 수 있습니다.

## 4. 권장 개발 순서

### 4.1 1단계: API 계약 고정

요구사항 명세서 7.1절의 API를 먼저 FastAPI Pydantic 모델로 정의합니다.

우선 구현할 API는 다음과 같습니다.

| 메서드 | 경로                                    | 목적                        |
| ------ | --------------------------------------- | --------------------------- |
| GET    | `/api/health`                           | 서버 상태 확인              |
| GET    | `/api/events`                           | 사건 목록 조회              |
| GET    | `/api/events/{event_id}`                | 사건 상세 조회              |
| POST   | `/api/events/{event_id}/status`         | 사건 상태 변경              |
| POST   | `/api/auth/signup`                      | 매장과 점주 계정 생성       |
| POST   | `/api/auth/login`                       | 세션 ID 발급                |
| POST   | `/api/auth/logout`                      | 세션 폐기                   |
| GET    | `/api/auth/me`                          | 로그인한 사용자와 매장 확인 |
| GET    | `/api/orders/drafts`                    | 발주 추천 목록 조회         |
| POST   | `/api/orders/drafts/{draft_id}/approve` | 발주 수량 승인              |
| POST   | `/api/ask`                              | 질문과 답변 처리            |
| GET    | `/api/ask/{session_id}/log`             | 질문 실행 로그 조회         |

내부 모듈 연결용 API는 다음과 같습니다.

| 메서드 | 경로                              | 목적                               |
| ------ | --------------------------------- | ---------------------------------- |
| POST   | `/internal/events`                | 영상 파이프라인에서 사건 후보 등록 |
| PATCH  | `/internal/events/{event_id}/vlm` | VLM 설명 결과 연결                 |

모든 입력과 출력은 Pydantic 스키마로 관리합니다. 사건 데이터는 요구사항 명세서의 `E015` 형식을 기준으로 하고, 회원가입 요청은 `store_name`, `email`, `password`, `display_name`을 받습니다. 이메일은 소문자로 정규화하고 비밀번호는 해시만 저장합니다.

### 4.2 2단계: DB와 Repository 구현

현재 메모리 Repository를 DB 설계서 기준의 PostgreSQL Repository로 교체합니다. 인증 영역은 `stores`, `users`, `auth_sessions`를 먼저 적용하고, 사건 영역은 사건 본체와 상태 이력을 하나의 트랜잭션으로 저장합니다.

우선 필요한 테이블은 다음과 같습니다.

```text
stores
users
auth_sessions
cameras
events
event_status_history
order_drafts
order_approvals
qa_sessions
tool_calls
```

매뉴얼 검색 기능을 구현할 때 다음 테이블을 추가합니다.

```text
manual_chunks
```

세션 인증은 다음 원칙을 따릅니다.

- 로그인 응답으로 세션 ID를 전달하고, 이후 요청은 `X-Session-ID` 헤더를 사용합니다.
- DB에는 세션 ID의 해시만 저장합니다.
- 로그아웃 시 `revoked_at`을 기록하고, 만료된 세션은 거부합니다.
- 보호 API는 세션의 사용자 `store_id`를 기준으로 매장 데이터를 제한합니다.

초기 모의 데이터에는 다음 사건을 사용합니다.

- `E014`: 카메라 끊김 사건
- `E015`: 쓰러짐 행동 사건

### 4.3 3단계: 사건 기능 구현

사건 기능은 현재 모의 데이터와 인메모리 Repository로 구현되어 있습니다. PostgreSQL Repository 교체 후 동일한 API 계약과 테스트를 유지합니다.

서버는 다음 업무 규칙을 담당합니다.

- 사건 후보 저장
- 사건 목록과 상세 조회
- 사건 상태 전이 검증
- 상태 변경 이력 저장
- 사건의 VLM 처리 상태 반환
- 끊김 사건의 영상과 점수를 빈 값으로 반환

사건 상태 전이는 다음 세 가지 경우만 허용합니다.

```text
unconfirmed -> confirmed
confirmed   -> resolved
unconfirmed -> false_alarm
```

허용되지 않은 전이는 `400 Bad Request`로 거부하고, 거부 사유를 응답합니다.

### 4.4 4단계: React 화면 연결

현재 연결 확인용 `App.jsx`를 다음 화면 구조로 확장합니다.

```text
App
├─ 사건 화면
│  ├─ 사건 목록
│  └─ 사건 상세
├─ 발주 화면
│  ├─ 추천 목록
│  └─ 승인 입력
└─ 질문 화면
   ├─ 질문 입력
   └─ 답변·출처·조회 조건
```

초기에는 라우터를 추가하지 않고 탭 방식으로 구현해도 됩니다. 서버 API와 데이터 구조가 안정화된 후 화면 컴포넌트를 파일별로 분리합니다.

### 4.5 5단계: 발주 기능 구현

발주 기능은 모델 연결보다 수량 계산 규칙을 먼저 구현합니다.

```text
필요량 = 예측 합계 + 안전재고 - 현재 재고 - 도착 예정
추천 수량 = 필요량을 박스 단위로 올림
```

요구사항 명세서의 예시는 다음과 같습니다.

```text
28 + 10 - 15 - 0 = 23
23개를 6개 단위로 올림 = 24개, 4박스
```

수량 계산은 별도 순수 함수로 구현하고 단위 테스트를 작성합니다.

승인 API는 다음 조건을 보장해야 합니다.

- 승인자, 승인 시각, 승인 수량 저장
- `sent_to_supplier`는 항상 `false`
- 현재 재고와 도착 예정은 변경하지 않음
- 승인된 발주 초안 상태 저장

### 4.6 6단계: 질문 API와 도구 구현

처음에는 실제 LLM 없이도 도구 구조와 로그를 먼저 구현합니다.

```text
query_records
search_manual
get_event_video
```

각 도구는 독립적인 함수로 구현하고, 질문 처리 루프에서 도구를 선택하도록 구성합니다.

반드시 먼저 적용할 안전장치는 다음과 같습니다.

- 허용 목록에 있는 도구만 실행
- 사건 번호와 날짜 형식 검증
- 다른 매장 기록 조회 차단
- 조회 오류와 0건 결과 구분
- 연속 도구 실패 2회 또는 전체 호출 5회 초과 시 중단
- 모든 도구 호출과 중단 사유 저장

실제 LLM 연결은 도구와 로그가 안정화된 뒤 진행합니다.

## 5. 권장 백엔드 폴더 구조

현재 `backend/app/main.py`에 있는 코드를 다음 구조로 단계적으로 분리합니다.

```text
backend/
└─ app/
   ├─ main.py
   ├─ config.py
   ├─ database.py
   ├─ schemas/
   │  ├─ event.py
   │  ├─ order.py
   │  └─ question.py
   ├─ models/
   │  ├─ event.py
   │  ├─ order.py
   │  └─ question.py
   ├─ repositories/
   │  ├─ event_repository.py
   │  └─ order_repository.py
   ├─ services/
   │  ├─ event_service.py
   │  ├─ order_service.py
   │  └─ question_service.py
   ├─ routers/
   │  ├─ events.py
   │  ├─ orders.py
   │  └─ questions.py
   └─ agent/
      ├─ loop.py
      └─ tools/
         ├─ query_records.py
         ├─ search_manual.py
         └─ get_event_video.py
```

각 계층의 책임은 다음과 같이 제한합니다.

| 계층       | 책임                       |
| ---------- | -------------------------- |
| Router     | HTTP 요청과 응답 처리      |
| Service    | 업무 규칙과 상태 전이 처리 |
| Repository | DB 조회와 저장             |
| Schema     | API 입력과 출력 형식       |
| Model      | DB 테이블 구조             |

## 6. 첫 번째 작업 목록

다음 서버 작업을 완료했습니다.

1. 사건 Pydantic 스키마 작성
2. `events`, `event_status_history` 저장 구조 작성
3. `GET /api/events` 구현
4. `GET /api/events/{event_id}` 구현
5. `POST /api/events/{event_id}/status` 구현
6. 허용·비허용 상태 전이 단위 테스트 작성
7. 모의 사건 `E014`, `E015` 등록
8. 회원가입·로그인·로그아웃·현재 사용자 조회 API 구현
9. 세션 ID와 비밀번호 해시 단위 테스트 작성

다음 프런트엔드 작업은 아직 남아 있습니다.

10. React 사건 목록 화면 구현
11. React 사건 상세 화면 구현
12. 확인, 오탐, 처리 완료 상태 변경 연결

이 작업으로 다음 요구사항을 우선 검증할 수 있습니다.

- `FR-REC-01` ~ `FR-REC-02`
- DB 설계서의 회원가입·세션 인증 API 계약

다음 항목은 React 화면 연결 후 검증합니다.

- `FR-UI-01` ~ `FR-UI-04`
- `FR-EVT-07` ~ `FR-EVT-08`의 모의 데이터 흐름

## 7. 구현 시 지켜야 할 서버 원칙

- AI 모델이 없어도 API와 화면이 동작해야 합니다.
- 사건 생성과 VLM 설명은 서로 차단하지 않아야 합니다.
- 끊김 사건에는 행동 점수와 영상을 넣지 않습니다.
- 점주 매장 번호를 기준으로 모든 기록을 제한합니다.
- 보호 API는 세션에서 확인한 사용자의 `store_id`를 사용합니다.
- 상태 변경, 승인, 도구 호출은 반드시 이력을 남깁니다.
- 비밀번호 원문과 세션 토큰 원문을 저장하지 않습니다.
- 로그아웃하거나 만료된 세션은 보호 API에 접근할 수 없습니다.
- 오류를 0건 결과로 바꾸지 않습니다.
- 승인 API는 실제 공급사 주문을 보내지 않습니다.
- 모든 시간은 한국 시간 기준 ISO 8601 형식으로 저장합니다.
- 임시 값, 모의 값, 합성 자료는 응답과 화면에서 구분합니다.

## 8. 검증 명령

### 백엔드

```powershell
cd backend
python -m compileall app
python -m unittest discover -s tests -v
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

실행 후 다음 주소를 확인합니다.

```text
http://localhost:8000/api/health
http://localhost:8000/docs
```

### 프런트엔드

```powershell
cd frontend
npm install
npm run lint
npm run build
npm run dev -- --host 0.0.0.0
```

실행 주소는 다음과 같습니다.

```text
http://localhost:5173
```

## 9. 완료 기준

현재 서버 단계는 다음 조건을 만족합니다.

- 서버를 실행하면 모의 사건 `E014`, `E015`를 조회할 수 있습니다.
- React 사건 목록에 사건 번호, 종류, 시각, 상태가 표시됩니다.
- 사건 상세에 카메라, 점수, 영상 상태, VLM 상태가 표시됩니다.
- 허용된 상태 전이만 성공합니다.
- 상태 변경 이력이 저장됩니다.
- 잘못된 상태 전이는 오류 응답을 반환합니다.
- 회원가입 시 이메일 중복을 거부하고 비밀번호 평문을 저장하지 않습니다.
- 로그인 시 세션 ID가 발급되고, `X-Session-ID` 헤더로 인증할 수 있습니다.
- 로그아웃하거나 만료된 세션으로 `/api/auth/me`에 접근할 수 없습니다.
- `python -m unittest discover -s tests -v`, `python -m compileall app`가 통과합니다.

아직 남은 완료 조건은 PostgreSQL 영속 저장소 연결, 세션 기반 매장 격리, React 회원가입·로그인 화면 연결입니다.

PostgreSQL Repository와 매장 격리를 완료한 다음 React 사건·인증 화면을 연결하고, 이후 발주 수량 계산과 승인 기능, 마지막으로 질문 도구와 LLM 연결을 진행합니다.
