# StoreOps AI 요구사항 명세서

무인매장 점주의 확인과 판단을 돕는 시스템이 무엇을 해야 하는지, 어떤 기술로 만들고 어느 부분에서 어떤 데이터를 쓰는지를 한 문서로 정리했습니다. 팀 수행 계획서와 함께 보는 문서이며, 기능 요구사항마다 기획서 쪽수를 근거로 달았습니다.

- **문서 버전**: v0.1 초안
- **작성일**: 2026-09-16
- **근거**: StoreOps_AI_v1_2.pdf, 01_AI_Agent_개요.pdf, 팀 수행 계획서
- **범위**: 8주, 팀원 6명 (A~F)

## 흐름별 데이터·기술·결과 개요

| | 쓰는 데이터 | 처리 기술 | 만드는 결과 |
|---|---|---|---|
| **사건** | AI Hub 영상, 팀 촬영 영상 (시연 중에는 카메라 영상과 연결 상태) | YOLO·추적 → I3D (끊김은 시간 규칙, 설명은 VLM) | 사건 후보와 1차 알림 (10초 영상, 다섯 점수, 뒤따르는 설명) |
| **발주** | 공개 판매 자료와 그 나라 휴일 파일 (시연은 합성 P001, 한국 공휴일) | pandas 전처리 → XGBoost (비교 기준은 최근 7일 평균, 수량은 계산식) | 추천 수량과 승인 초안 (공급사 주문은 나가지 않음) |
| **질문** | 점주 질문, 업무 기록, M001 규정 (규정은 조각 카드와 임베딩으로 저장) | LLM Agent와 조회 도구 3개 (매뉴얼 검색 도구 속은 RAG) | 근거가 붙은 답변 (원문, 출처, 조회 조건) |

**모이는 곳**: 업무 기록 DB와 점주 화면 3개 — 사건 상태 이력, 발주 승인 이력, 질문과 도구 호출 로그가 쌓입니다. 서버·DB·화면 기술은 1주차 결정(6절 제안).

> 세 흐름은 서로 영향을 주지 않고 결과와 점주의 판단만 업무 기록에 쌓입니다 *(기획 6p)*. 색은 계획서와 같이 노란색이 사건, 청록색이 발주, 파란색이 질문입니다.

## 1. 개요

### 1.1 목적

무인매장에는 점주가 상주하지 않으므로, 매장 안의 이상 상황과 카메라 끊김을 빨리 알고, 발주 수량을 정하고, 지난 기록과 규정을 찾아보는 일을 점주가 원격으로 해야 합니다. StoreOps AI는 이 세 가지 일을 돕되, **AI는 후보 제시와 추천과 조회까지만 하고 확인, 오탐 처리, 발주 승인은 점주가 한다**는 원칙을 따릅니다. 이 문서는 그 원칙 아래에서 시스템이 갖춰야 할 기능, 품질, 데이터, 기술을 정의해 팀원 모두가 같은 기준으로 개발하고 검수하도록 하는 데 목적이 있습니다.

### 1.2 범위

**범위 안**
- 사건 경로 1(행동 분류)과 경로 2(카메라 끊김), VLM 설명
- 수요 예측, 추천 수량 계산, 승인 초안 저장
- 질문 Agent와 도구 3개, 매뉴얼 검색
- 점주 화면 3개와 업무 기록
- 모델 학습·평가, 시연 환경

**범위 밖**
- 공급사로 실제 주문 전송, 재고·도착 예정 자동 변경 *(기획 24p)*
- Agent에 의한 발주 승인이나 알림 발송 *(26p)*
- 영상 속 인물의 신원 식별이나 저장 *(15p)*
- 실제 매장 운영 데이터 사용
- 휴대폰 푸시 알림 (시연에서 화면 알림으로 대신할 수 있는지 확인 중)

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 사건 후보 | 시스템이 만든 사건. 점주가 확인하기 전까지는 사실로 보지 않습니다. |
| 묶음 | 한 사람을 오려낸 2~4초 길이의 영상 조각. 행동 분류의 입력 단위입니다. |
| 추적 번호 | 여러 프레임에서 같은 사람을 잇기 위해 붙이는 임시 번호. 신원과 무관합니다. |
| 기준값 | 행동 분류 점수를 사건으로 볼지 가르는 값. 현재 0.60은 임시 값입니다. |
| 기준 시간 | 카메라 끊김을 사건으로 볼지 가르는 시간. 현재 60초는 임시 값입니다. |
| 오탐 | 점주가 영상을 보고 실제 사건이 아니라고 판단한 사건 후보. |
| 승인 초안 | 점주가 승인한 발주 수량을 저장한 기록. 공급사에 전송되지 않습니다. |
| 조각 카드 | 규정 문서를 나눈 한 조각. ID, 원문, 문서명·버전·절, 임베딩으로 이뤄집니다. |
| 도구 | Agent가 부를 수 있는 조회 기능. query_records, search_manual, get_event_video 세 개입니다. |
| 합성 자료 | 시연을 위해 기획서 예시 값에 맞춰 만든 가짜 판매 기록. |
| 모의 값 | 모델이 준비되기 전에 모듈을 연결하려고 쓰는 기획서 예시 값(E014, E015, 0.78, P001). |

### 1.4 표기 규칙

요구사항 번호는 `FR-EVT`(사건), `FR-ORD`(발주), `FR-QNA`(질문), `FR-UI`(점주 화면), `FR-REC`(업무 기록), `NFR`(비기능), 데이터는 `D`로 시작합니다. 근거 표시의 "기획"은 기획서, "교안"은 AI Agent 개요 교안, "계획서"는 팀 수행 계획서입니다. "추가 제안"은 두 문서에 없지만 이 명세서에서 새로 제안한 항목이라 팀 확정이 필요합니다.

- **확정**: 기획서나 계획서에서 정해진 것
- **임시 값**: 값은 있으나 검증 후 바뀔 수 있는 것
- **미정**: 담당과 기한 안에 정할 것
- **제안**: 이 문서가 권하는 안, 팀 확정 필요

## 2. 시스템 개요

### 2.1 구성

시스템은 독립적으로 돌아가는 세 흐름과, 그 결과를 모으는 업무 기록 DB, 그리고 점주 화면 3개로 이뤄집니다. 사건과 발주는 사람이 순서를 정해 둔 **Workflow**이고, 질문은 LLM이 도구를 고르는 **Agent**이며, 그중 매뉴얼 검색 도구의 속이 **RAG**입니다 *(교안 41p)*. 절차가 매번 같은 사건과 발주는 순서를 고정해 결과를 예측할 수 있게 하고, 질문은 종류와 필요한 조회 순서가 매번 달라서 Agent로 둡니다 *(교안 21~22p)*.

### 2.2 사용자

| 사용자 | 하는 일 | 권한 |
|---|---|---|
| 점주 | 알림 받기, 사건 영상 확인과 상태 변경, 발주 수량 수정과 승인, 문장으로 질문 | 자기 매장 기록만 조회·변경 |
| 팀(운영자) | 기준값·기준 시간 등 설정 조정, 로그와 평가 결과 확인, 시연 환경 운영 | 설정 파일과 로그 접근 |
| 질문 Agent | 점주 질문에 맞는 조회 도구 선택과 입력값 생성 | 조회만 가능, 변경·승인·발송 불가 |

### 2.3 운영 환경

- 시연 매장은 한 곳(`S01`)이며 카메라는 한 대 이상(`CAM-01` 등)입니다.
- 시연 환경은 서버, DB, 점주 화면을 한 대에서 띄우고, 모델 학습은 별도의 GPU 환경에서 합니다.
- 모든 시각은 한국 시간(UTC+9) 기준입니다.

### 2.4 제약과 가정

- 기간은 8주, 인원은 6명입니다. 가장 어려운 행동 분류 학습은 A가 전담합니다.
- 데이터는 공개 자료, 동의받은 팀원의 촬영 영상, 팀이 만든 문서와 합성 자료만 씁니다 *(기획 11p)*.
- 데이터 수령과 모델 학습이 늦어질 수 있으므로, 1~2주차에 모듈 사이 데이터 형식(7.3절)을 확정하고 모의 값으로 전체를 먼저 연결합니다.
- 재고 조건은 기획서 가정을 따릅니다. 안전재고 10개, 6개들이 박스입니다 *(기획 21, 23p)*.
- 외부 통계(314%, 1만 1,015건 등)는 도입 배경일 뿐 이 프로젝트의 측정값이 아닙니다 *(기획 3p)*.

### 5.3 흐름별 데이터 처리 순서

**사건 영상**
1. AI Hub 2건을 1주차에 신청하고, 동의한 팀원이 다섯 분류와 몸을 낮추는 동작처럼 헷갈리는 정상 동작을 연기해 촬영합니다.
2. 동의서를 보관하고 정해진 방식으로 얼굴을 처리합니다.
3. "12~15초 쓰러짐"처럼 구간으로 라벨을 달고, 묶음 하나에 라벨 하나를 붙여 교차 검수합니다.
4. 같은 촬영 회차나 연기자가 학습, 검증, 시험에 섞이지 않게 나눕니다.
5. YOLO 위치, 추적 번호, 같은 사람 오려내기, 2~4초 묶음 순으로 전처리합니다.
6. I3D를 전이학습하고, 분류 불균형에 대응하며, 기준값별 오탐과 놓침을 봅니다.
7. 실행 결과는 사건 후보 JSON, 10초 영상, 사진 3장으로 DB에 들어갑니다.

**판매 기록**
1. 판매 자료의 표 구조와 사용 조건을 1주차에 확인해 자료 현황표에 적습니다.
2. 휴일은 판매 자료와 같은 나라의 파일을 붙입니다.
3. 기록이 없는 날은 0으로 채우지 않고, 휴무, 품절, 기록 누락을 구분해 적습니다.
4. 최근 7일 평균, 지난주 같은 요일 판매량, 요일, 공휴일 여부를 만듭니다.
5. 시간 순서로 앞 기간은 학습, 뒤 기간은 확인에 쓰고, 7일 평균은 확인하는 날마다 새로 계산합니다.
6. 같은 확인 기간에서 XGBoost와 7일 평균의 오차(MAE 등)를 비교합니다.
7. 시연은 합성 P001(최근 7일 평균 13.6개, 지난주 같은 요일 12개, 03-15 실제 17개)과 가정 재고로 계산해 발주 초안 JSON을 만듭니다.

**규정 문서와 기록**
1. M001 v0.1을 작성합니다. 3절에는 기획 29p의 두 문장을 넣습니다.
2. 문서를 조각으로 나눠 조각 카드(예: `M001-C03`)를 만듭니다. 조각 크기는 D가 정합니다.
3. 한국어를 지원하는 임베딩 모델로 벡터를 만들어 벡터 저장소에 넣습니다.
4. 질문과 가까운 조각을 찾고, 기준에 못 미치면 근거 부족으로 답합니다.
5. 찾은 조각의 원문과 출처를 LLM에 넘겨 답변 문장마다 근거를 잇습니다.
6. 기록 조회는 상대 날짜를 한국 시간 범위로 바꾸고, 매장 번호를 고정하고, 결과 상태를 세 가지로 나눠 돌려줍니다.
7. 평가셋은 기록, 규정, 영상, 여러 도구, 실패 유도 다섯 유형으로 만듭니다.

| 도구 | 언제 쓰나 | 입력 | 출력 | 실패 조건 | 성공 확인 |
|---|---|---|---|---|---|
| `query_records` | 건수나 기록을 묻는 질문 | store_id (필수), record_type (필수, `event` 또는 `order_draft`), date_from·date_to (필수, 한국 시간 ISO 8601) | status (`ok`, `error`, `not_received`), count, record_ids, 받은 조회 조건 | 날짜 형식 오류, 시작이 끝보다 늦음, 허용 밖 기록 종류, 다른 매장 번호, 저장소 오류 | status가 ok이고 count가 record_ids 개수와 같음 |
| `search_manual` | 규정과 절차를 묻는 질문 | question (필수), doc_scope (선택) | status (`ok`, `insufficient_evidence`), answer, evidence(chunk_id, 원문, 문서명, 버전, 절) | 기준 이상 가까운 조각 없음, 빈 질문 | 답변 문장마다 근거 조각이 하나 이상 |
| `get_event_video` | 특정 사건 영상을 요청할 때 | event_id (필수, E와 숫자 세 자리) | status, video_uri, 구간, 카메라, 사건 종류, 시각 | 형식 오류, 없는 번호, 영상 없음(끊김 사건) | 영상 주소가 있고 사건 정보가 기록과 일치 |

### 7.3 모듈 사이 데이터 형식

1~2주차에 이 형식을 고정하면 모델이 없어도 각자 모의 값으로 개발할 수 있습니다. 앞의 두 개는 계획서 7절과 같고, VLM 결과는 이 명세서에서 추가로 제안하는 형식입니다.

**사건 후보 (B → E, D)**
```json
{
  "event_id": "E015",
  "store_id": "S01",
  "camera_id": "CAM-01",
  "source": "behavior_model",
  "event_type": "fall",
  "occurred_at": "2026-03-14T21:12:00+09:00",
  "clip": {"uri": "…", "length_sec": 10},
  "scores": {"normal": 0.15, "fall": 0.78,
             "fight": 0.04, "vandalism": 0.02,
             "littering": 0.01},
  "threshold": 0.60,
  "vlm": {"status": "pending"},
  "status": "unconfirmed"
}
```
끊김 사건(E014)은 `"source": "time_rule"`, `"gap_sec": 90`, `"threshold_sec": 60`을 쓰고 clip과 scores를 비웁니다.

**발주 초안 (F → E)**
```json
{
  "product_id": "P001",
  "forecast": {"d1": 16, "d2": 12, "total": 28},
  "safety_stock": 10,
  "on_hand": 15,
  "incoming": 0,
  "need": 23,
  "pack_size": 6,
  "recommended": {"qty": 24, "boxes": 4},
  "shortage_before_arrival": 13,
  "approved": {"qty": 18, "boxes": 3,
               "by": "owner-01",
               "at": "2026-03-14T22:05:00+09:00"},
  "status": "draft_saved",
  "sent_to_supplier": false
}
```

**VLM 결과 (C → E)** *(제안)*
```json
{
  "event_id": "E015",
  "status": "done",
  "frames": ["…/start.jpg", "…/mid.jpg", "…/end.jpg"],
  "observed": "관찰한 내용",
  "uncertain": "확실하지 않은 점",
  "owner_checks": "점주가 확인할 일",
  "missing_fields": [],
  "model": "선정 후 기입",
  "created_at": "2026-03-14T21:12:20+09:00"
}
```
status는 `pending`, `done`, `failed`, 끊김 사건은 `not_applicable`입니다. 생성 시각은 설명을 위한 값입니다.
