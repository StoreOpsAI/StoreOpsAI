## 🚀 1. 개발 프로세스 (GitHub Flow)

GitHub Flow는 `main`을 안정적인 상태로 유지하면서, 각 작업을 별도의 브랜치에서 진행하고 Pull Request(PR)로 검토한 뒤 `main`에 반영하는 협업 방식입니다.

우리 팀은 `main` 브랜치와 작업별 브랜치를 사용합니다. `main`에는 직접 푸시하지 않고, 변경 사항은 PR을 통해서만 반영합니다. 기능은 `feature/작업이름`, 버그 수정은 `fix/작업이름`처럼 브랜치 이름을 정해주세요.

### 💻 작업 순서

1. **최신 `main` 가져오기** — 새 작업을 시작할 때 기준이 되는 코드를 최신 상태로 맞춥니다.
   ```bash
   git checkout main
   git pull origin main
   ```

2. **작업 브랜치 만들기** — 작업마다 새 브랜치를 만들고, 그 브랜치에서만 수정합니다.
   ```bash
   git checkout -b feature/login
   ```

3. **변경 사항 커밋하기** — 관련된 변경을 확인하고 커밋 컨벤션에 맞춰 저장합니다.
   ```bash
   git add 변경한_파일
   git commit -m "feat: 로그인 기능 추가"
   ```

4. **작업 브랜치 푸시하기** — GitHub에 작업 내용을 올립니다.
   ```bash
   git push -u origin feature/login
   ```

5. **PR 만들기** — GitHub에서 작업 브랜치를 `main`으로 합치는 PR을 엽니다. PR의 대상(base)은 `main`, 비교(compare)는 작업 브랜치인지 확인하고, 무엇을 왜 변경했는지 설명합니다.
6. **리뷰 및 수정** — 팀원의 피드백을 확인하고 필요한 수정 사항을 같은 작업 브랜치에 커밋한 뒤 푸시합니다. 변경 사항은 열린 PR에 자동으로 반영됩니다.
7. **승인 및 머지** — 최소 1명 이상의 팀원에게 리뷰와 승인을 받은 후 PR을 `main`에 머지합니다. 머지된 변경만 `main`에 반영되며, 작업 브랜치는 삭제해도 됩니다.

> 루트의 `README.md`를 수정하는 PR을 머지하면 기존 루트 README가 수정됩니다. 별도의 README 파일을 추가하는 것이 목적이라면 다른 파일명이나 폴더 경로를 사용하고, 찾기 쉽도록 루트 README에서 링크하세요.

작업 중인 브랜치에 최신 `main`의 변경 사항을 반영해야 한다면, 팀에서 정한 방식으로 `main`을 작업 브랜치에 병합한 뒤 테스트하고 푸시하세요. 같은 부분을 서로 다르게 수정해 충돌이 발생하면 충돌 내용을 직접 정리한 뒤 커밋해야 합니다.

## 📝 2. 커밋 컨벤션 (Commit Convention)

작성한 커밋 메시지만 보고도 변경 사항을 파악할 수 있도록 아래 규칙을 따릅니다.

### 📌 커밋 메시지 구조
```text
태그: 한 줄 요약

- 필요한 경우 자세한 설명 추가 (본문)
```

### 🏷️ 주요 태그 종류

| 태그 (Tag) | 설명 | 예시 |
| :--- | :--- | :--- |
| **`feat`** | 새로운 기능 추가 | `feat: 카카오 소셜 로그인 구현` |
| **`fix`** | 버그 및 오류 수정 | `fix: 이메일 중복 체크 에러 수정` |
| **`docs`** | 문서 수정 (README, 주석 등) | `docs: README 개발 환경 안내 추가` |
| **`style`** | 코드 포맷팅 (세미콜론, 줄바꿈 등) | `style: 코드 인덴트 및 포맷 정렬` |
| **`refactor`**| 코드 리팩토링 (로직 변경 없는 구조 개선) | `refactor: 로그인 컴포넌트 구조 분리` |
| **`chore`** | 빌드 설정, 패키지 매니저, 환경 설정 변경 | `chore: 라이브러리 의존성 패키지 설치` |
